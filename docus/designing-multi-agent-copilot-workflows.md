Project Workspace Custom Agent Workflow Guide
This workspace configuration framework outlines how to design, structure, and deploy multi-agent workflows using GitHub Copilot's `.agent.md` file specification inside your project repository.
---
1. Architectural Patterns
   The Hub-and-Spoke Pattern
   The Orchestrator (Hub): Interacts with the user, determines the execution plan, translates user intent into distinct prompts, dispatches jobs, and aggregates results.
   The Workers (Spokes): Single-purpose, context-isolated specialists (e.g., security auditor, test generator, performance analyst). They have access to specific tools (`file_search`, `execute`) and execute sub-tasks invisibly.
```
       [ User Prompt ]
              │
              ▼
     ┌─────────────────┐
     │  Orchestrator   │ <── (User-Invocable: true)
     └────────┬────────┘
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
┌───────┐ ┌───────┐ ┌───────┐
│Worker1│ │Worker2│ │Worker3│ <── (User-Invocable: false)
└───────┘ └───────┘ └───────┘
```
---
2. Directory Structure and Rules
   For your IDE (like IntelliJ or VS Code) to register your custom workflow seamlessly, organize your project workspace using the explicit `.agent.md` file suffix within the project-level metadata directory:
```text
Your-Project-Root/
└── .github/
    └── agents/
        ├── lead-architect.agent.md           # The Parent Orchestrator
        ├── spring-boot-reviewer.agent.md     # Specialized Worker 1
        └── test-coverage-expert.agent.md     # Specialized Worker 2
```
---
3. Reference Implementation Templates
   File 1: The Worker Agent (`.github/agents/spring-boot-reviewer.agent.md`)
   Workers should be completely isolated from the user's explicit selection pool. They ingest raw prompts generated by the orchestrator, process files using targeted tools, and return a clean data stream.
```yaml
---
name: Spring Boot Code Reviewer
description: Senior Java specialist checking application architecture, REST APIs, and production readiness.
argument-hint: Pass the relative paths of the Java classes requiring technical evaluation.
user-invocable: false
tools: ['file_search', 'open_file']
---
You are a highly analytical, strict background static analysis engine. 
Your objective is to evaluate the code context provided in your prompt against Spring Boot 3.x production-readiness best practices.

Focus areas:
- REST Controller design (correct HTTP verbs, response entities, exception handling).
- Database layer hygiene (lazy loading, transaction boundaries, query optimization).
- Resilience patterns (circuit breakers, timeouts, retry logic).

Output Constraints:
- Do not provide conversational fluff or greetings. 
- Return findings in raw Markdown bullet points sorted by severity: [CRITICAL], [WARNING], [OPTIMIZATION].
```
File 2: The Orchestrator Agent (`.github/agents/lead-architect.agent.md`)
The parent orchestrator requires the special `agents` capability tool. Without this specific string in the `tools` array, the execution environment will block all downstream `task()` dispatch requests.
```yaml
---
name: Lead Architect
description: High-level architectural manager that designs systems and delegates review pipelines.
tools: ['file_search', 'open_file', 'agents']
---
You are the Lead Architect. Your primary responsibility is evaluating system architectures and coordinating background workers. 

When a user provides a workspace prompt or asks for an application review, adhere to this exact structural workflow:

1. Locate Context: Identify and read the codebase targets using 'file_search' or 'open_file'.
2. Execute Pipeline: Dispatch sub-tasks to your specialized workforce. Do not attempt to complete code-level inspections yourself.
   
   A. Trigger the Code Reviewer:
      Call the tool: task(agent_type="Spring Boot Code Reviewer", prompt="Evaluate the classes located in the src/main/java/com/example/controller/ folder for runtime vulnerabilities and rest patterns.")
   
3. Aggregate and Synthesize:
   Wait for the background agent to return its raw findings. Take that output and wrap it in a polished, developer-friendly executive summary. Present the findings transparently to the user, mapping out remediation action items.
```
---
4. Execution Workflow (How It Runs)
   User Invocations: The developer enters the IDE chat interface, inputs `@Lead Architect`, and submits a prompt: "Review our new checkout workflow implementation."
   Context Resolution: The `Lead Architect` agent searches the repository, targets the changed files, and packages them up.
   Delegation Loop: The orchestrator encounters the `task()` tool call. The IDE freezes user-facing text stream rendering and creates an inner execution loop context.
   Isolated Evaluation: The `Spring Boot Code Reviewer` runs in the background. It reads the files, applies its system directives, compiles a raw markdown report, and returns it upstream.
   Final Aggregation: The `Lead Architect` handles the raw report, applies its formatting constraints, and yields a comprehensive, single-screen response to the developer.
---
5. Critical Engineering Rules
   Hyphenation Precision: Always use `user-invocable: false`. Accidentally omitting the hyphen (`user invocable`) breaks the configuration parser and exposes internal workers to the end-user.
   String Multi-Match: The `agent_type` argument inside the orchestrator's `task()` execution block must be an exact literal match to the `name` attribute declared in the target worker’s front matter.
   Flushing Workspace Caches: IDE extensions cache the agent registry layout strictly. If a modified worker fails to hide or update its behavior, apply a minor text mutation inside the `.agent.md` file and save to trigger a registry invalidation.
